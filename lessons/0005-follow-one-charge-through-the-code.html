You've missed exactly one kind of question, three times: transfer_data with no amount (Q6), who commits after charge_share (L3 Q3), the proxy flags (L3 Q4). All the same seam — the drop from the design to the line that does it. Two of those three live inside a single function. So we're going to read it, slowly, and trace one charge from intent to durable outcome. By the end, "who commits?" won't be a guess — you'll see that charge_share cannot.

Everything here is the same charge you diagnosed in Lesson 1 and the same money flow from Lesson 2 — now at the grain of the actual code. Nothing new to believe; a lot to locate.

The claim to hold onto

One sentence, and the whole lesson proves it payments.py never commits. The caller (settlement.py) owns the transaction. That is what makes record-first a structure instead of a promise everyone has to keep.

Beat 1 — settle_event stamps intent · COMMIT #1

Before a cent moves, the choreographer writes down what it's about to do. From settlement.py, inside the settle loop:

payment = Payment(
    event_id=event.id, attendee_id=attendee.id,
    state="none",                                 # nothing collected yet
    charge_requested_at=datetime.now(timezone.utc),  # the stamp: WHEN
    charge_requested_cents=charge,                # the stamp: HOW MUCH
)
session.add(payment)
await session.commit()          # ← COMMIT #1 · intent is now durable

Notice the state is none and the two stamps are set. That is literally Row 2 from Lesson 1 — the dangling shape. If the process died on the very next line, this row would sit in the DB saying "I was about to charge $30 and I never finished" — findable by query, retryable, safe. The scary row you learned to recognise is manufactured on purpose, right here.

And hold this thought: settle_event has a session — it's a parameter. It is allowed to commit. Keep your eye on who holds the session.

Beat 2 — charge_share moves the money · NO commit

Now the call into payments.py. Read the signature before anything else:

async def charge_share(payment, attendee, planner, actual_cents) -> Payment:
This is the answer to L3 Q3, and it's in the signature There is no session here. A commit is session.commit() — you can only commit a session, and this function doesn't hold one. It cannot commit; it isn't physically able to. The one file that talks to Stripe is, by its own parameter list, incapable of making anything durable.

So what does it do? It checks the stamp, calls Stripe, and mutates the payment object in memory. The guard first — record-first, enforced:

if payment.charge_requested_at is None:
    raise ValueError("stamp the intent before moving money")
if payment.charge_requested_cents != actual_cents:
    raise ValueError("amount drifted from the stamped intent")

It refuses to charge an amount that doesn't match what COMMIT #1 recorded — because a retry has to re-send the identical request for Stripe's idempotency replay to work. Then the money move:

intent = await stripe.PaymentIntent.create_async(
    amount=actual_cents, currency="usd",
    customer=attendee.stripe_customer_id,
    payment_method=attendee.stripe_payment_method_id,
    confirm=True, off_session=True,
    on_behalf_of=planner.stripe_account_id,
    transfer_data={"destination": planner.stripe_account_id},  # ← Q6, in situ
    idempotency_key=f"{payment.id}:charge",
)

There's your Q6 — transfer_data with a destination and no amount, so the full $30 transfers out and, because it's a destination charge, the ~$1.17 fee is debited from your platform. One line, both facts. And the idempotency_key is the fixed {payment.id}:charge — the string that makes a retry replay instead of double-charge.

Then the outcome is written to the object, in memory:

# success:
_move(payment, "paid")                    # state → paid, in memory only
payment.charged_cents = actual_cents
payment.stripe_payment_intent_id = intent.id
return payment                            # ← hands the object back. No commit.

# decline (stripe.CardError):
_move(payment, "unpaid")                   # state → unpaid, in memory only
payment.state_reason = decline_code
return payment                            # ← still no commit.

Every write in Beat 2 is in memory. As far as the database is concerned, nothing has changed since COMMIT #1 — the row is still state=none with the stamp set. The money may have already moved at Stripe. The DB doesn't know yet. That gap is the dangling window, and you're looking at the code that opens it.

Beat 3 — the caller commits · COMMIT #2

Back in _collect in settlement.py — the function that called charge_share:

await charge_share(payment, attendee, planner, cents)   # mutated in memory
await session.commit()          # ← COMMIT #2 · the outcome is now durable
if payment.state == "paid":
    return Outcome(attendee.id, "paid")

There is your L3 Q3. The commit that turns "paid" from an in-memory fact into a durable one lives in settlement.py — the coordinator that holds the session — not in payments.py. charge_share moved the state; _collect made it real.

Why it has to be split this way

This is the part worth owning, because it's your own record-first decision expressed as machinery. Record-first needs two commits in a guaranteed order: intent before the Stripe call (COMMIT #1), outcome after (COMMIT #2). The only way to guarantee an order between two commits is to have one piece of code own both. If charge_share committed its own outcome, a future edit could commit before Stripe answered, or slip a second write between the stamp and the call — and the ordering would silently rot. By handing payments.py no session, the order isn't a rule anyone has to remember. It's a fact about the code's shape.

That's Lesson 3's "placement beats discipline," at the finest possible grain: the safety is in the parameter list.

The crash map — Lesson 1, now located in the code Where the process dies decides the row you find:
before COMMIT #1no row / pristine — nothing was intended
between #1 and #2dangling (state=none, stamp set) — money maybe moved; press Retry, same key replays the real outcome
after COMMIT #2paid or unpaid — fully recorded, no ambiguity
The same table you memorised in Lesson 1 is just a map of which line you were on when the wifi dropped.
