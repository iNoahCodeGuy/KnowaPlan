Lesson 6 · ~12 minutes · The loop that charges your whole group without ever betting the group on one card

You're about to wire gross_up into this function, so you should own its choreography first. Lesson 5 gave you one commit; Lesson 4 gave you one charge. This is the whole settlement: what happens when you press Settle with four friends on the roster and one of them has an expired card, one has no card, and your wifi dies halfway through.

Nothing here is a new decision. This is decisions.md 2026-07-16 (settlement mechanics) and the recovery-labeling half of the success_url entry — both yours — read at the grain of the code that implements them.

The four phases

settle_event is long but it is only ever doing one of four things:

1 · CloseAn open event closes first — settlement beginning is a close (state_machines.md). Any other state than closed refuses outright.
2 · ResolveUndecided rows get the planner's pre-set default. Absences move no money, so they land in one bulk commit.
3 · ChargeThe per-attendee loop — the rest of this lesson.
4 · SettleEvent → settled, settled_at stamped, report returned.

The split sits between 2 and 3, and it is two lines:

divisor = len(participants)
share   = event.total_cost_cents // divisor if divisor else 0

Note what participants means: everyone present. Zero participants is a valid settlement — charge nobody — which is why the if divisor guard exists instead of a crash.

The planner is a divisor, never a charge

Your rule from 2026-07-16: a playing planner counts in the split but is never charged — routing their money to their own account minus Stripe's cut is pure waste. Here is that entire decision, as one line:

charged = [
    (rsvp, attendee)
    for rsvp, attendee in participants
    if attendee.id != planner.attendee_id      # <- the whole rule
]
Two lists, one difference participants sets the divisor. charged sets who gets a Payment row. The planner is in the first and filtered out of the second — so they lower everyone's share by playing, and pay nothing through Stripe. Delete that if and you'd charge yourself, then pay a fee to send your own money to yourself.

The loop that can't be aborted

Four friends. Marcus's card declines. Does Ana still get charged?

She does, and the reason is purely structural — the try lives inside the loop, so a failure ends one iteration, not the settlement:

for rsvp, attendee in charged:
    ...                       # record-first stamp + COMMIT
    try:
        outcomes.append(await _collect(...))
    except (stripe.StripeError, RuntimeError):
        result = "dangling" if payment.state == "none" else "unpaid"
        outcomes.append(Outcome(attendee.id, result))

Move that try outside the for and one friend's expired card would abandon everyone after them: uncharged friends, an event stuck in closed, and you finding out by text.

The subtlety: a decline never reaches this except

This is the part worth slowing down on. stripe.CardError is a subclass of stripe.StripeError — I checked in your venv, it's True — so it looks like a decline would be caught right here. It isn't, because it never gets this far: charge_share catches CardError itself and returns a row marked unpaid.

The principle, in your own comment “The card said no” is an outcome, not an error. A decline is the system working — an answer arrived. So it becomes a row state, not an exception. What reaches the loop's except is only the case where no answer arrived: a network or API failure (StripeError), or a PaymentIntent that came back in a status other than succeeded (RuntimeError, raised by your own code — and not a Stripe class, which is why it's named separately in that tuple).

Reading the label: dangling or unpaid

One line decides which recovery the planner is offered, and it does it by reading the row rather than the exception:

result = "dangling" if payment.state == "none" else "unpaid"
state == "none"The charge itself is unconfirmed. Stripe may or may not have taken the money → dangling, retry with the same key and stamped amount.
past noneThe charge already resolved (unpaid is committed); only the link mint failed → unpaid, recovery is a fresh link.

You paid for this distinction in production. The first smoke walk mislabeled every failure as dangling, so a cardless row whose link mint failed wore a Retry button that retry_dangling correctly refused — recovery dead-ended (decisions.md 2026-07-16). The fix is the line above.

What a second press of Settle does

Settlement is resumable, and this is where the money safety lives. Before the loop, every existing Payment row for the event is loaded into existing, keyed by attendee. Each iteration then asks what already happened to this person:

paidSkip. Report paid. Nobody is charged twice.
unpaidSkip, and deliberately do not re-mint — the stored link is still live (one payable link per row).
other terminalRefunded or abandoned are audit rows; a new attempt is walk-in territory, deferred.
none + stampDangling from the crashed run: retry with charge_requested_cents — the stamped amount, never a recompute.
no rowFresh: stamp intent, commit, then charge.

That last-but-one row is the one to hold onto. A recomputed amount would change the Stripe parameters, and identical-params is exactly what makes a replayed idempotency key safe. Re-sending the stamp is what lets you press Settle again at the court without thinking about it.

Where your gross_up wiring goes

Now the payoff, because you're about to edit these exact lines. One number splits into two, and the whole job is keeping them straight:

shareNet. total // divisor — what you must end up with. Stays exactly as it is.
billedGross. gross_up(share, …) — what goes on the card, and therefore what lands in the charge_requested_cents stamp and flows into _collect.

Two traps, both already pinned by the red tests waiting for you:

  • The cap at cap_at_estimate must compare gross to gross. Today's min(share, estimate) with a grossed estimate would compare a net against a gross and quietly bill the un-grossed number — you'd absorb the entire fee while believing you had capped.
  • The stamp takes the billed amount. It already means “how much,” and charge_share refuses any drift from it — so the retry path inherits gross-up correctness for free, with no change to retry_dangling at all.
