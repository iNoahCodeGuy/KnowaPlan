The shape of the codebase

Lesson 3 · ~10 minutes · Twelve files, four layers, and one rule about who may write what

You asked what you need to know about this codebase. The full answer is now a reference — the KnowaPlan map, which includes the whole learning path — but the map only works if you can read its skeleton. That skeleton is this lesson: which file is allowed to do what, and why the invariants you grilled depend on it.

Here's the claim to test everything against: your decisions are enforced by placement. Record-first, table-checked transitions, capability URLs — none of these survive because everyone is careful. They survive because the code that could violate them isn't allowed to live where the violation would happen.

The four layers

  EDGE      web.py + templates, main.py     token → row, form → service
  SERVICES  rsvps.py, events.py,            flow, state writes, COMMITS
            settlement.py
  MONEY     payments.py                     the only file that calls Stripe
  MEMORY    models.py                       rows remember
  LAW       state_machines.py               tables legislate
            ── plumbing: db.py, config.py, bootstrap.py ──

Four placement rules, each carrying a decision you already own:

Law is data, not code. state_machines.py is your transition tables, transcribed — no behavior, terminal states map to the empty set. Services consult it via can_transition(); nothing else decides legality. An illegal move is a loud ValueError, never a silent write.
Only services assign state. rsvp.state = … appears in rsvps.py, events.py, settlement.py (and payments.py for the Payment machine) — always behind a table check. It appears in web.py zero times. I verified that today, mechanically. A route cannot typo a transition, because a route never writes one.
Only payments.py talks to Stripe — and it never commits. It mutates rows in memory and makes the API call; the caller owns the transaction. This is record-first, load-bearing: your 2026-07-13 decision needs intent committed BEFORE the Stripe call and the terminal state after — so the commit points must belong to the choreographer (settlement.py), not to the code standing next to Stripe. (settlement.py does import stripe — but only to catch its error types, never to call it.)
The edge translates; it doesn't decide. web.py turns a token into a row — each helper queries ONLY its own column, which is why an /e/ link can never act as an /admin/ link — parses the form, calls a service, renders a template. Even the buttons it renders come from allowed_choices(), so the UI physically can't offer an illegal move.
Why placement beats discipline Suppose a future you, at midnight, adds a route that sets payment.state = "paid" directly. Nothing about Python stops you. But the review diff shows a state write in web.py — a category error, visible without reading a single line of logic. Layering turns subtle bugs into obvious ones. That's the whole trick, and it's why "where does this code go?" is a correctness question here, not a style question.

One tap to one charge

Trace the two writes that matter. Wednesday night, event open; Marcus taps Going:

POST /r/{token}/respond
  web.py      finds the Rsvp by rsvp_token (that column only)
  rsvps.py    respond(): event still open? choice a response state?
              can_transition(RSVP, "pending", "going")?  → rsvp.state = "going"
              session.commit()                            ONE write, done

Thursday, after the game, the planner settles. This is the same shape — edge → service → money — but now the service's commit choreography is the safety mechanism:

POST /admin/{token}/settle
  web.py         finds the Event by admin_token; success_url from request.base_url
  settlement.py  settle_event():
                   close if open (table-checked) → floor(total ÷ present)
                   skip the planner (divisor, never a charge)
                   COMMIT #1  Payment row + charge_requested_at
                              + charge_requested_cents        ← intent is durable
  payments.py      charge_share(): refuses a missing stamp or
                   drifted amount → Stripe PI, key "{id}:charge"
                   → succeeded: state = "paid" (in memory)
  settlement.py    COMMIT #2  terminal state                  ← outcome recorded

Now the crash story you designed reads directly off the layout: a crash between COMMIT #1 and COMMIT #2 leaves stamp-set, state-none — the dangling row you learned to spot in Lesson 1 — and retry_dangling replays the stamped amount under the same idempotency key. One attendee's decline or API error is caught in settlement.py's loop, so the rest of the group still settles.

The plumbing, in three sentences

db.py hands every request its own database session and closes it after — FastAPI's dependency-with-yield pattern, verbatim. It sets expire_on_commit=False because, per the SQLAlchemy asyncio docs, that's what lets code touch an object's attributes after a commit without triggering hidden IO — forbidden in async. config.py reads the environment (lazily, so tests can rig it), and bootstrap.py creates tables only when you explicitly run it — your 2026-07-16 decision that schema changes are a command, never startup magic.
