The KnowaPlan map

Reference · what a developer needs to know · grounded in the code as of 2026-07-21

KnowaPlan splits a fixed cost (a pickleball court) across whoever actually shows up. Attendees RSVP through capability URLs — no accounts — and optionally save a card; at close the planner marks attendance and each present attendee's true share is charged from their saved card, collected via a tap-to-pay link, or recorded as paid directly (Venmo/Zelle/cash) once the planner confirms it. No holds, no webhooks, no background jobs in v0. It custodies real money, so correctness beats speed everywhere.

Live status, 2026-07-21 Both money legs are verified against live Stripe with real cards: a saved-card auto-charge ($1.00) and a tap-to-pay link ($1.66), both reading KNOWAPLAN SPLIT on the statement, both transferred to the connected account, the roster poll observed flipping unpaid → paid in production. First real event: the pickleball club, 2026-07-29.

The one rule that makes the invariants enforceable Every state-machine column is assigned only after a can_transition() check — in services and in payments.py, never in web.py. And payments.py never commits: it mutates rows in memory and talks to Stripe; the caller owns the transaction. That split is what makes record-first possible — the commit points are chosen by the choreographer (settlement.py), not by the code that moves money.

Every file, one line

main.py Assembles the app: includes the router, global error page (copy deliberately makes no claim about money), /health.
web.py All routes + Jinja2 templates. Looks up each token in its own column only, parses forms, delegates to services, renders. Never assigns a state column. Its own commits: row creation and Stripe-id bookkeeping (after a card save or link poll).
rsvps.py RSVP service: get_or_create_rsvp (the /e/ entry — find-or-create by canonicalized phone, mints the /r/ token, auto-links a playing planner), respond, allowed_choices (UI can never offer an illegal move — under the uniform rule every answer offers the other two).
phone.py One pure function, normalize_phone: strip non-digits, drop a leading US 1, require exactly 10. Identity IS the phone, so every store and compare goes through it — autofill's (619) 555-0123 and typed digits must be one person, or a duplicate orphans a saved card and can dodge the never-charge-the-planner match. (2026-07-21)
events.py Pre-money event writes: open_rsvps (draft→open), cancel_event — refuses if ANY Payment row left pristine none (a crashed settle may have moved money).
settlement.py The record-first choreographer: mark_attendance, close_rsvps, settle_event (close → floor split → skip planner → stamp intent in ONE commit → charge/link per attendee, failures contained per attendee), retry_dangling (stamped amount, same idempotency key). Refuses outright if a nonzero per-person share is under Stripe's 50¢ floor — before any stamp.
payments.py The only Stripe call surface: save card (SetupIntent), charge_share (off-session PI, fires from none only), create_payment_link / poll_link_status (Checkout Session, one payable link per row), mark_paid_direct (planner-confirmed Venmo/Zelle/cash — kills any live link BEFORE the state write), refund_charge — a guarded stub until walk-ins ship.
fees.py Pure integer arithmetic for the Stripe-fee gross-up — no Stripe calls, no DB. Bodies are still stubs; the property tests are xfail(strict) so the step stays visibly open. See open items.
models.py Five tables: Planner, Attendee, Event, Rsvp, Payment. FOUR token columns, minted by column default (an insert cannot forget). Payment also carries the direct-payment fields (claimed_at/claimed_via = an attendee's unverified claim; paid_direct_at = the planner's confirmation). The DB stores state; it does not enforce transitions.
state_machines.py Pure data — the transition tables transcribed from state_machines.md, plus can_transition(). No behavior. On disagreement, the doc wins.
db.py Lazy async engine (import never needs a DB), pool_pre_ping for Railway's idle reaping, get_session — one session per request via FastAPI's dependency-with-yield; expire_on_commit=False because async forbids the implicit IO that attribute expiry would trigger.
config.py pydantic-settings; env beats .env. Normalizes any postgres:// URL onto the asyncpg driver so a managed host's variable pastes verbatim.
bootstrap.py create_all, run explicitly — never at startup. It only ADDs tables: after a model change, drop/recreate the dev DB. Alembic arrives at live dogfood.
.claude/hooks/money_guard.py Enforced (not advisory) guard: denies any .py edit using the Refund API without the refund-guard: captured-only marker. Fails closed; pinned by tests/test_money_guard.py.

The four state machines

Eventdraft → open → closed → settled → archived; open|closed → cancelled. Close is manual or settle-triggered — never tied to start time.
RSVPpending → any answer; and any answer ↔ any answer while the event is open (uniform rule, 2026-07-21 — "backing out is planner territory" was a hold-era fossil). going → attended|no_show stays the planner's write at settlement.
Paymentnone → paid | unpaid; unpaid → paid | abandoned; paid → refunded. No holds — authorized, voided, auth_failed died with the 2026-07-15 pivot. unpaid → paid now has three triggers: the link pays, the poll records it, or the planner confirms a direct payment.
Attendanceunconfirmed → present | absent, resolved at settlement. Lives on the Rsvp row (same grain).

Money invariants — the review checklist

Given a diff to the money path, check it against these. Each traces to a decisions.md entry.

Integer centsAll amounts. Never float. (bool is rejected too — True must not read as 1¢.)
Record-firstONE commit writes the attendance change + charge_requested_at + charge_requested_cents BEFORE the Stripe call; terminal state after. The DB always knows at least as much as Stripe. (2026-07-13, -16)
Idempotency keysDerived from (payment.id, operation) — "{id}:charge". Retry = same key, same params. New attempt = new row, fresh key by construction. (2026-07-08)
Charge from none onlyAfter a decline (unpaid), the tap-to-pay link is the ONLY recovery — a saved card is never re-fired for that row. (2026-07-16)
One payable link per rowRe-minting retires the old session first — refuse if it already collected. Links are shown once, never stored beyond the session id. (2026-07-16)
Table-checked writesEvery state assignment passes can_transition() — an illegal move raises, never silently writes.
Planner is a divisor, never a chargeCounts in floor(total ÷ present); no Payment row exists for them. (2026-07-16)
Default charges actualCap-and-absorb (at the frozen estimate snapshot) is an active planner choice; silence never absorbs. (2026-07-15, -16)
Refund = reversal of collected money, onlyEnforced by the money_guard hook, not prose. Stub until walk-ins. A direct payment can't be refunded through Stripe at all — the planner reverses it out-of-band.
A claim is not a paymentAn attendee saying "I paid you on Venmo" sets a flag and leaves the row unpaid — the roster keeps counting it as owed until the planner confirms. Never assume collected. (2026-07-21)
Kill the link before saying paidmark_paid_direct expires any live Checkout session BEFORE the state write — the inverse of record-first, because this call destroys a collection path instead of creating one. Crash after expire = unpaid row + dead link (re-mint recovers); the reverse would invite a double payment. (2026-07-21)
50¢ floor, refused earlyStripe rejects sub-50¢ charges. settle_event raises before any stamp or present-marking; the preview hides the buttons. Service-level, so a direct POST can't skate past. NOT a floor in _validate_cents — a partial refund may legitimately be smaller. (2026-07-21)
One spelling per personEvery phone store and compare goes through normalize_phone. Identity is the phone; two spellings would be two people, and one of them can't be charged. (2026-07-21)

Deployment

ImageDockerfile: python:3.12-slim, pip install, copy app/, run uvicorn on $PORT. Host: Railway, with managed Postgres.
Load-bearing flags--proxy-headers --forwarded-allow-ips '*' make request.base_url honor X-Forwarded-Proto/Host behind Railway's proxy. Without them every share link and Checkout success_url the app prints is an internal http:// hostname.
Env varsDATABASE_URL (any postgres:// form — normalized to asyncpg) · STRIPE_SECRET_KEY · STRIPE_PUBLISHABLE_KEY (browser island) · PLANNER_ACCOUNT_ID (the CONNECTED account that receives money — never the platform's own id) · CREATE_PASSWORD (unset = event creation refused).
Schemapython -m app.bootstrap once per fresh DB. It cannot ALTER — model change = drop/recreate (dev) or hand-ALTER (deployed, until Alembic).
Runtime lessonstripe's *_async methods need httpx at RUNTIME — it was dev-only once, the image lacked it, every deployed Stripe call 500'd (found 2026-07-16). Pinned in requirements.txt.
Connect account shape The connected account needs BOTH configurations: merchant (be merchant of record — on_behalf_of) and recipient (receive transfers — transfer_data.destination). The dashboard wizard created a merchant-only v2 account, so every charge failed insufficient_capabilities_for_transfer. Fixed by requesting configuration.recipient.capabilities.stripe_balance .stripe_transfers via POST /v2/core/accounts/{id} (Stripe-Version: 2025-08-27.preview). (2026-07-21)
The check that lied — worth internalizing The v1 account endpoint reported transfers: active, charges_enabled: true, currently_due: [] — and transfers were nonetheless impossible, because on a v2 account that field is a projection, not the capability that governs receiving them. The v2 view said it plainly: applied_configurations: ["merchant"]. Third instance of the same failure mode in this project (after the fee-payer theory and the success_url assumption): a plausible check that appears to pass. The reliable move is to reproduce the actual failing call and read Stripe's own error, not to consult a status field adjacent to it.
The operational fact that explains everything There are no webhooks, no schedulers, no background jobs. Nothing happens unless a request happens. Payments land on the roster because loading the roster polls outstanding links; auto-settle and the maybe→declined timer are deferred with the scheduler; settlement runs when the planner taps Settle. If a state looks stale, the question is "which request would have refreshed it?"

Testing

BoundaryNever the live Stripe API — conftest injects mock_stripe. Transactions are pinned against in-memory SQLite (aiosqlite): real commits, still hermetic.
Pinning tests19 files, 367 passing + 9 xfail(strict) (the open gross-up). test_state_machines.py (full transition matrix) · test_payments.py (exact-kwarg contracts) · test_money_guard.py (the hook fails closed) · test_settle_web.py (settle outcomes incl. mint-failure labeling) · test_pay_direct.py (the link dies before the paid write) · test_phone.py (autofill and typed digits are one person).
Known blind spotsMocks can't see fees (Lesson 2's $3.51 discovery), SQLite ignores VARCHAR widths (the 64-char overflow, 2026-07-16), and no test can see your Stripe account's configuration (the merchant-only account, 2026-07-21). All three burned once already: anything account-shaped or Postgres-shaped must be verified against the real thing, deliberately.

Adding a feature here

  1. Read the canonical docs for the territory you're touching; a contradiction means stop and align, not code around it.
  2. Align before acting (owner rule, 2026-07-16): every shaping decision — behavior, schema, names, defaults, wording — is put to the owner with a recommendation BEFORE files change. Money and state-machine code: mechanism explained, owner reviews or writes the body.
  3. Route in web.py (token lookup → parse → delegate → render); flow and state writes in a service behind can_transition; Stripe calls in payments.py with a (payment.id, operation) key; columns in models.py (then drop/recreate the dev DB).
  4. Pin behavior in tests (mock Stripe); run .venv/bin/pytest and ruff check.
  5. Record any decision made in decisions.md — append-only, with alternatives and why.
