Payment row — field guide

One row per attendee per event. Everything you need to know about their money is in it. Print this.

The one rule state is the only column that says whether money moved. Every other column is evidence, and two of them lie if you read them alone.

What each column means

ColumnMeansTrap
state none · paid · unpaid · refunded · abandoned. The verdict. —
charge_requested_at We were about to call Stripe. Written before the call, in the same transaction as the attendance change. Set ≠ charged. It means tried.
charge_requested_cents How much we were about to charge. Stamped with the timestamp, same transaction. Intent, not fact. Compare to charged_cents.
charged_cents What actually collected. The money truth. NULL until a charge lands.
stripe_payment_intent_id The latest charge attempt — succeeded, declined, or link-collected. Present on a decline too. Never read as proof of payment.
stripe_checkout_session_id The outstanding tap-to-pay link. One payable link per row, ever. Stale after ~24h. Re-mint, don't reuse.
state_reason Why we landed here: no_card, a Stripe decline code, abandoned. Cleared to NULL once the link collects.
attempt Always 1 until walk-ins ship. A genuinely new attempt is a new row, so the idempotency key is fresh by construction. —

Diagnose it

Read state first, then charge_requested_at. Those two answer it. Everything below follows.

What you seeWhat happenedWhat you do
No row at all Never billed, by design. Either they were marked absent / no_show, or they're you — the planner's linked attendee counts in the split divisor but never gets a row. Nothing. This is correct.
state=none
stamp NULL		 Pristine. Nothing attempted. The event hasn't settled yet. Nothing. Settle when ready.
state=none
stamp set		 Dangling. We told the DB we were about to charge, then Stripe never answered — crash, timeout, dropped connection. The money may or may not have moved. This is the only state where you genuinely do not know. Roster shows “charge requested — unconfirmed”. Press Retry charge. It re-sends the same idempotency key with the stamped amount, so Stripe replays whatever really happened. Safe. Do not hand-fix in the dashboard.
state=paid
charged_cents set		 Collected. Money is in your Connect account (minus Stripe's cut). charged_cents is how much. Nothing.
state=unpaid
reason=no_card		 They RSVP'd without saving a card. Expected, not a failure. Text them the link. Get fresh link on the roster if the old one is stale.
state=unpaid
reason=a decline code		 Saved card declined off-session at close. A PaymentIntent exists at Stripe — it is the record of the decline, not a charge. Send the link. The saved card is never re-fired for this row — the link is the only recovery, and it's on-session, which clears most off-session declines anyway.
state=abandoned You stopped chasing. Terminal. Settle up out of band.
state=refunded A collected charge was reversed. Not shippable in v0 — refund_charge raises NotImplementedError until walk-ins land.

Three things that will fool you

1 — A PaymentIntent id is not a receipt A declined charge writes stripe_payment_intent_id too. Stripe really did create a PaymentIntent; it just ended in requires_payment_method instead of succeeded. The column means “latest attempt”. state means “did we get the money”.
2 — unpaid is not failure It's the normal resting state for anyone without a card. Half your roster may sit here after a clean settle. It means “the link is the path”, not “something broke”.
3 — Dangling is the only scary one Every other state is a fact. Dangling is an unknown, and it's the one the whole record-first design exists to create — deliberately. A crash mid-charge leaves a row you can find with a query instead of a charge you'd find in an angry text.

Where to look

The roster /admin/{admin_token} — card-on-file badge, attendance, payment state, and the recovery buttons. This is your console. Whoever holds this link is the planner.
The DB select * from payments where event_id = …; when the roster isn't enough.
Stripe Last resort. If the DB and Stripe disagree, the DB is the thing you fix through the app — Retry, or poll. Hand-editing in the dashboard breaks the invariant that the DB knows at least as much as Stripe.
